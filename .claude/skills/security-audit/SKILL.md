# 安全审查技能

本项目的"安全体检"：像体检医生一样把代码从头到脚查一遍，找出安全隐患，输出中文报告。

## 检查清单（用户 2026-09-17 拍板）

1. **敏感信息泄露**：代码里硬编码的密码、令牌（token / API key / 密钥）、
   身份证号 / 手机号 / 银行卡号等个人信息。
2. **SQL 注入漏洞**：SQL 语句是否用字符串拼接用户输入（危险做法）；
   正确做法是参数绑定（`?` 占位符 + prepare），本项目标准 SQLite 用法见 `src/main/db.ts`。
3. **配置文件明文敏感信息**：`.env*`、`*.yml`、`*.json` 等配置文件里的明文密码/密钥；
   含个人信息的本地配置文件是否被排除出版本库（.gitignore 检查）。
4. **其他隐患**（主动排查）：调试输出泄漏敏感信息、打开外部链接未校验协议
   （如 `shell.openExternal` 要只放行 http/https）、依赖库已知漏洞（跑 `npm audit`）、
   打包配置中的危险项、权限配置异常等。

## 执行流程

1. **定范围**：`src/`、`scripts/`、根目录配置文件（`package.json`、`electron-builder.yml`、
   `*.json`、`*.yml`、`.env*`）、`.claude/` 与 `.gitignore`；node_modules 与打包产物除外。
2. **逐项检查**：按清单四条逐个文件排查，记录每一处问题（文件:行号、什么问题、风险等级、建议修法）。
3. **跑依赖体检**：执行 `npm audit` 检查依赖库有没有已知漏洞。
4. **出报告**：按下方模板输出中文报告。
5. **修复需批准**：默认只出报告、不动代码；用户明确说"修"之后才动手，修完复检并汇报。

## 风险等级表（放在报告开头，让用户一眼看懂）

| 等级 | 含义 | 处理 |
|---|---|---|
| 🔴 高危 | 会直接威胁数据安全或隐私 | 必须马上修 |
| 🟡 中危 | 有风险，但暂时不会直接受害 | 建议尽快修 |
| 🟢 低危 | 风险很小 | 有空再修 |
| ✅ 安全 | 没发现问题 | 无需处理 |

## 注意事项

- 只查不动：审查中发现的问题一律写进报告，修复必须等用户批准。
- 不误报：白名单/测试数据不算泄露；内网地址、本地路径不算敏感信息；先判断"这条信息泄露出去会有什么后果"再定级。
- 涉及删除/覆盖任何文件（哪怕是 .gitignore 加一行）也要先向用户说明并获得同意。
