# 单元测试技能

本项目的"质检流水线"：用 Vitest 为代码写检查程序、运行检查、出中文报告。

## 测试环境（已配置好，勿改动）

- 测试工具：Vitest（配置文件 `vitest.config.ts`）
- 检查程序统一放在 `tests/` 目录，文件命名 `*.test.ts`
- 执行命令：`npm test`（一键跑全部检查）

## 关键安全约定（必须遵守）

1. **绝不碰真实账本**：测试 `src/main/db.ts` 时，必须先 `vi.mock('electron')` 把
   `app.getPath` 指向系统临时目录的测试专用文件夹（参考 `tests/db.test.ts` 现有写法），
   测试结束用 `closeDb()` 关连接后删除临时目录。
2. **绝不修改内置分类**：涉及分类顺序、图标跟随等测试，一律先 `createCategory` 自建测试分类，
   测完靠 `beforeEach` 清理（`DELETE FROM categories WHERE id > 内置分类数`）。
3. 每个检查从干净状态开始：`beforeEach` 里清空 records 表与自建分类。

## 执行流程

1. **找零件**：读目标代码，挑出纯逻辑功能（计算、校验、转换、查询规则），优先测
   "容易算错、容易改坏"的部分；界面组件（.vue）默认不测。
2. **写检查**：在 `tests/` 新建或扩展 `*.test.ts`，风格参照现有测试文件（中文注释、
   中文报错文案断言）。先想好"喂什么数据 → 预期什么结果"，再写断言。
3. **跑检查**：执行 `npm test`。
4. **查红灯**：有失败时先判断是哪边的问题——
   - 生产代码真错了 → 修代码，再跑测试；
   - 检查程序预期写错了 → 修测试（注意 CSV 转义、边界移动等"看着不对实则正确"的规范行为）。
5. **改完必复跑**：`npm test` 全绿才算完。

## 测试报告格式（写给用户看，必须中文、通俗）

按以下模板输出（用户 2026-09-17 拍板定稿：表格卡片式 + 终端图形 + 模块明细 + 执行过程），禁止技术黑话：

```
## 测试报告

📊 X 项通过 · ❌ Y 失败 · 用时 N 秒

各模块检查项数量（条形图）：

模块名A     ████ 4
模块名B     ██ 2
…
通过率：████████████████████ 100%（或按实际比例画条）

| 模块 | 检查内容 | 结果 |
|---|---|---|
| … | … | ✅/❌ |

🔍 tester 测试工程师（subagent）的执行过程
1. （干了什么，一步一行）
2. …
3. …

**失败项说明**（若有）：每项用一句通俗话解释——哪里坏了、为什么坏、已修好还是待处理。

**结论**：一句话总结。
```

要点：
- **条形图**：用 `█` 字符画，长度按各模块检查项数量，终端里直接可见，不生成图片文件。
- **表格卡片式**：按"模块"分行概括检查内容（如内置分类、记一笔、账单查询、月度统计、分类管理、CSV 导出），结果列只用 ✅ / ❌。
- **模块明细**：表格每行"检查内容"要具体（如"金额 0/负数/小数全部拦截"），不写"共 3 项"这种空话。
- **执行过程**：标题必须写"tester 测试工程师（subagent）的执行过程"，让用户一眼知道这部分是 subagent 干的活；内容按实际干的事列步骤（读代码→写检查→跑测试→修正/复跑→出报告）。
- 若失败项超过 3 个，失败说明改用列表逐条写。

若用户要求修复测试中发现的问题，修完后复跑并更新报告。
